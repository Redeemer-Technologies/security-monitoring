Security Plugin for Rock

Overview #

This plugin provides a set of tools to help Rock administrators monitor and improve the security of their Rock instances. It provides a daily email summary of potential security issues with your Rock configuration and a set of tools to analyze your IIS logs from within Rock. The Lava Approvals tool can scan your system for unsafe Lava and SQL and, with the help of AI, help you understand how to harden your Lava.

Installing this plugin will add the following components to your Rock instance:

Component Type Purpose
Security Audit Job Rock Job Runs a suite of pass/fail checks against Rock security settings and known configuration issues and finds Lava scripts needing approval
Process IIS Logs Job Rock Job Incrementally converts IIS W3C log files to compressed parquet files in App_Data for performant querying.
Installed Plugins -> Rock Security Page A set of pre-built pages for IIS monitoring and Lava Approvals
Power Tools -> IIS Log Query Page A block that allows you to write SQL queries against your IIS logs.

Installation #

  1. Download the latest release from for your Rock version.
  2. Configure the Security Audit job and the Process IIS Logs job under Admin Tools › System Settings › Jobs Administration.
  3. Monitor your IIS logs under Installed Plugins -> IIS Logs, or run ad-hoc queries from Power Tools -> IIS Log Query

Note

Check the Process IIS Logs job to ensure it was able to find your IIS logs.

IIS Logs

Overview #

Analyzing your IIS logs can be an important part of monitoring for and investigating potential security incidents. This plugin provides a job that processes your IIS logs into a format optimized for querying from within Rock. By default, the plugin looks for IIS W3C log files in the standard log directory, but you can configure a custom path if needed.

The plugin creates a set of pages under Installed Plugins -> IIS Analytics that are pre-configured with a set of reports. These pages can be customized or extended with additional IIS Log Query blocks as needed.

Additional Log Fields

To get the most out of the built-in reports you should enable the cs-host and sc-bytes fields on your IIS logs. These will allow you to see which Rock site a request was made against as well as how many bytes were returned by that request.

Process IIS Logs Job #

This job incrementally converts IIS W3C log files into compressed parquet files for faster querying. The job tracks file offsets between runs so only new, complete lines are processed each invocation. By default, it will process your logs every five minutes, which can be lengthened or shortened if necessary.

Warning

The first time this job runs, it will process all of the logs for your configured retention period. This may take up to ten minutes depending upon how many logs are on your system.

IIS Log Query Block #

This block, similar to the built-in Dynamic Data block, allows you to write SQL Queries against the parquet files produced by the Process IIS Logs job. It can render the results either as a Rock grid or through a Lava template. The provided IIS Analytics pages make use of this block and ChartJS to display their data.

Query syntax #

Queries must contain the literal token [[logs]] where the parquet source should be injected. SQL queries must be written for DuckDB, which has a slightly different syntax than Rock's usual T-SQL queries. Notably, DuckDB uses LIMIT instead of TOP for limiting results, and uses " for quoting identifiers instead of [ and ]. For example, the following query would return the 100 most recent log entries:

SELECT *
FROM [[logs]]
ORDER BY "date" DESC, "time" DESC
LIMIT 100

Block Attributes #

Default SQL QuerySQL
The query to use for the block. If show query on page is enabled, this query can be edited at runtime by the user.
Query Parametersstring, optional
Similar to the dynamic data block, this is a semi-colon separated list of query parameters that can be used within the SQL query, in the format param1=value1;param2=value2. Note, when using the parameters in your query, use a named parameter with a dollar sign, for example WHERE "date" = $param1.
DateRangeDate range, optional
Limits the logs included in the query to those within the selected range. When omitted, all available parquet files (up to the maximum file limit) are included. Using a smaller range if you know the approximate date of the logs you're looking for can speed up query performance by reducing the number of logs that need to be scanned.
MaximumParquetFilesInteger
Caps the number of parquet files read in a single query as a guard against unbounded scans.
ResultRenderModeEnum
Either Grid for a standard Rock grid or Lava for a custom template rendered against the query results. A default lava template is included to show you the syntax.


Security Audit

Overview #

The Security Audit is a Rock job that runs a series of checks against the current Rock configuration and returns a pass/fail summary in the job result. When email notifications are enabled on the job, the same summary is sent through the standard Rock service job notification email setting.

Checks #

The following checks are run each time the Security Audit job is executed.

Security role memberships

Snapshots active members of the Rock Administrators, Staff Workers, and Staff-Like Workers roles on the first run. Subsequent runs fail when membership changes and list the people added or removed since the previous snapshot.

Binary file type security

Checks all BinaryFile types, excluding any whitelisted types defined in the job settings, and fails the check for any type that allows public view access.

Document type security

Checks all Document types, excluding any whitelisted types defined in the job settings, and fails the check for any type that allows public view access.

Disable Predictable Ids

Fails when Rock's DisablePredictableIds setting is not enabled. This setting prevents predictable integer identifiers from being accepted by Rock's file handlers (GetFile.ashx.cs, GetImage.ashx, and GetAvatar.ashx). When this setting is disabled, those handlers can be polled with incremental ids to probe for insecure files.

Password Regular Expression

Reads the PasswordRegularExpression global attribute. The check fails when the value is blank or still set to Rock's default of \w{6,255}, which is far too weak for secure passwords.

Workflow group memberships

Checks Group Member Add actions in workflows to ensure any public workflows guard against permissions escalation attacks.

Injection-style content

Searches Person and Location fields for values containing potential injection-style content. Matches do not indicate exploitation, but flag values that should be reviewed and cleaned.

Warning

If you see an address or a person record returned by the injection audit, You should use SQL to review and clean up the values. Loading the person record or location in Rock may cause malicious code to run on your system.

Security plugin version

Downloads security-plugin-versions.json from the published source and compares the installed plugin version with the latest version published for the current Rock version. This helps ensure that the information from the plugin is the latest available. It also what includes any known security issues with your current version of Rock in the audit email.

Job settings #

BinaryFileType WhitelistBinary File Type list, optional
A list of binary file type names to exclude from the binary file type auth check. If you have a file type that you intentionally want to be open to the public, you can select it and the job will not warn you about that file type.
DocumentType WhitelistDocument Type list, optional
Comma-delimited list of document type names or Guids to exclude from the document type check.
Results Email AddressesEmail address list, optional
Comma-delimited list of email addresses to receive the audit results.

Lava Approvals

Overview

Lava Approvals is a tool to help you stay on top of the Lava and SQL scripts that are being deployed at various places around your Rock instance. The Security Audit job will scan common places that Lava and SQL are found, such as in HTML blocks, Dynamic Data blocks, Lava and SQL runs in workflows, Lava shortcodes, and more. When it finds content that contains Lava tags, it will create an entry on the Installed Plugins -> Rock Security -> Lava Approvals page in Rock.

From the Lava Approvals page, you can review the content of each script and and approve it if it meets your security standards. Approval is only required once for each unique Lava script, as determined by the SHA-256 hash of the script content. If a previously approved script changes in any way, it will reappear on the Lava Approvals page for review and approval.

You may optionally specify an OpenAI API key and model on the Security Audit job and the Lava Approvals List block. If provided, The security audit job will scan each discovered Lava script for vulnerabilities with the configured AI model and provide an AI analysis along with each Lava Approval. The AI analysis is meant to help you understand the potential security implications of the script and give you guidance on how to improve it. The AI will include a risk rating of low, medium, or high along with an explanation of the reasoning behind the rating and suggestions for improving the script's security.

Where possible, the plugin will attempt to determine if a vulnerable Lava script is accessible to in some way and mark that script with a public tag on the approvals screen. Any scripts marked as public will have their risk rating escalated.
